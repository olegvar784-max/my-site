# my-site — сайт-визитка с CI/CD

![CI/CD](https://github.com/olegvar784-max/my-site/actions/workflows/ci-cd.yml/badge.svg)

Практическое задание «CI/CD для веб-разработчика». Выполнил: Варнавский О. В., группа К841.

- Сайт: https://olegvar784-max.github.io/my-site/
- Конвейер: `.github/workflows/ci-cd.yml` (GitHub Actions → GitHub Pages)

## Состав

| Файл | Назначение |
|---|---|
| `index.html` | главная страница: заголовок, изображение, блоки «Обо мне», «Навыки», «Учебные работы», «Контакты» |
| `style.css` | стили: flexbox и grid, адаптивность до ширины 360 px, светлая и тёмная тема |
| `script.js` | переключение темы с запоминанием выбора, счётчик посещений |
| `test.js` | проверки страницы: заголовок, изображение с `alt`, блок «Обо мне», подключение файлов |
| `package.json` | скрипты `lint` (htmlhint), `test`, `build` (сборка в `dist/`) |

Локальный запуск проверок: `npm install`, `npm run lint`, `npm test`, `npm run build`.

## Конвейер

```
push / pull_request → [ci: checkout → setup-node 20 → npm install → lint → test → build
                           → проверка ссылок (lychee) → артефакт site-build]
                    → [deploy (только main): download-artifact → configure-pages
                           → upload-pages-artifact → deploy-pages] → сайт обновлён
```

Дополнительные задания: бейдж статуса конвейера в этом файле и шаг проверки ссылок
`lycheeverse/lychee-action` (в режиме `--offline` проверяются ссылки на файлы внутри сайта).

## Эксперименты

| № | Действие | Результат |
|---|---|---|
| 1 | Незакрытый `<div>` в `index.html` | ошибка на шаге «Run linter»: `Tag must be paired, missing: [ </div> ] (tag-pair)`; deploy не запускался |
| 2 | Скрипт `test` заменён на `exit 1` | ошибка на шаге «Run tests» (код завершения 1); build и deploy не выполнялись |
| 3 | Ветка `feature/x` и Pull Request в `main` | выполнено только задание ci; deploy пропущен (условие `if`) |

## Ответы на вопросы

**Чем отличается CI от CD?**
CI (непрерывная интеграция) — автоматическая проверка каждого изменения: при каждом push код
собирается, проверяется линтером и тестами, и ошибка обнаруживается сразу, а не перед выпуском.
CD — следующий этап. Continuous Delivery означает, что проверенная сборка всегда готова к выпуску,
но выпуск запускает человек. Continuous Deployment выпускает её автоматически. В этом проекте
используется Continuous Deployment: после успешного CI в ветке `main` сайт публикуется на GitHub Pages
без ручных действий.

**Что произойдёт, если тесты завершатся ошибкой на этапе CI?**
Шаг `npm test` вернёт ненулевой код, задание ci будет помечено как неуспешное, а следующие шаги
(сборка, артефакт) не выполнятся. Задание deploy не запустится, и на сайте останется предыдущая
рабочая версия. Причину ошибки показывает журнал шага во вкладке Actions, автор коммита получает
уведомление.

**Для чего используется директива `needs: ci` в задаче развёртывания?**
По умолчанию задачи workflow выполняются параллельно. `needs: ci` делает deploy зависимой:
она ждёт завершения ci и запускается, только если ci завершилась успешно. Так на сайт не попадает
код, не прошедший проверку. Кроме того, deploy получает артефакт, который ci к этому моменту уже
сохранила.

**Что такое артефакт и для чего он передаётся между задачами?**
Артефакт — файлы, полученные в результате выполнения задачи и сохранённые GitHub после её
завершения, здесь — каталог `dist/` с готовым сайтом. Каждая задача выполняется на отдельной чистой
виртуальной машине, поэтому файлы из ci в deploy сами не попадают. Передача артефакта гарантирует,
что публикуется именно та сборка, которая прошла линтер и тесты, а не собранная заново.

**Почему развёртывание не запускается на Pull Request?**
Pull Request — предложение изменений, которые ещё не проверены и не приняты в `main`. Для него
нужна только проверка: CI показывает, можно ли сливать ветку. Публикация непринятого кода заменила
бы рабочий сайт непроверенной версией. Поэтому у deploy стоит условие
`if: github.ref == 'refs/heads/main'`: у Pull Request ссылка имеет вид `refs/pull/<номер>/merge`,
и задача пропускается. Сайт обновится после слияния PR, когда в `main` придёт push.
